# D1 사고 대응 runbook

## 원칙

- 운영 D1에 복원하지 않는다.
- 가장 최근 백업을 바로 신뢰하지 않고 별도 테스트 D1에서 먼저 검증한다.
- Google Drive에는 암호화된 `.age` 파일만 보관한다.
- 개인키·OAuth token·Cloudflare 자격증명을 문서나 채팅에 기록하지 않는다.
- 확인되지 않은 데이터 손실 범위를 추측해서 완료 처리하지 않는다.

## 1. 데이터 이상 신고

1. 사용자 화면, 발생 시각, 여행 ID, 영향을 받은 기능만 기록한다.
2. 현재 운영 배포 버전과 D1 migration 상태를 읽기 전용으로 확인한다.
3. 쓰기 작업을 추가로 실행하지 않는다.
4. 애플리케이션 오류인지 D1 데이터 손상인지 분리한다.
5. 운영 export가 필요하면 범위와 시각을 제시하고 별도 승인을 받는다.

## 2. 백업 생성 실패

1. 스크립트 종료 코드와 실패 단계만 기록한다. 키나 SQL 내용을 기록하지 않는다.
2. 출력 폴더에서 `.d1-backup-*`, `.sql`, `.partial` 잔존 여부를 확인한다.
3. 잔존 평문이 있으면 경로와 파일 크기만 보고하고 삭제 승인을 받는다.
4. 완성된 `.sql.age`의 크기가 0이거나 SHA-256을 얻지 못하면 Drive에 올리지 않는다.
5. 같은 입력으로 반복 실행하기 전에 Cloudflare·디스크·`age` 중 실패 경계를 확정한다.

## 3. 복원 리허설

1. 복원 대상이 새 빈 테스트 D1인지 이름과 Cloudflare 화면에서 이중 확인한다.
2. 운영 DB 이름과 테스트 DB 이름이 다른지 확인한다.
3. 암호화 파일의 SHA-256을 백업 기록과 대조한다.
4. `restore-d1-test.ps1` 계획 모드를 먼저 실행한다.
5. 별도 승인 뒤 `-ExecuteTestRestore`, `-ConfirmTestDatabaseRestore`, `-ConfirmEmptyTestDatabase`를 모두 지정해 테스트 D1에만 복원한다. 마지막 확인은 새 빈 테스트 D1임을 Cloudflare 화면에서 확인했다는 뜻이다.
6. Cloudflare·SQLite 메타데이터를 제외한 사용자 테이블 전체 row count와 표본 데이터를 대조한다.
7. 평문 임시 파일이 남지 않았는지 확인하고, 암호화되지 않은 디스크에서 물리적 안전 삭제를 보장하지 않는 잔여 위험을 기록한다.
8. 테스트 D1 삭제는 복원 증거 보존 기간을 정하고 별도 승인 뒤 수행한다.

## 4. 개인키 분실

- 외장하드의 비밀번호 암호화 `key.age`와 해당 비밀번호가 모두 있어야 기존 백업을 복호화할 수 있다.
- `key.age` 또는 비밀번호 중 하나라도 잃으면 기존 `.age` 백업을 복호화할 수 없다.
- Drive 파일만으로 복구할 수 있다고 주장하지 않는다.
- 오프라인 복구 사본의 존재와 접근 권한을 확인한다.
- 모든 사본을 잃었으면 새 키로 향후 백업을 시작하되 기존 백업을 복구 가능하다고 표시하지 않는다.

## 5. 개인키 노출 의심

1. 키 값을 출력하지 않는다.
2. 노출 위치·시각·접근 가능 범위만 기록한다.
3. 기존 키를 새 백업에 사용하지 않는다.
4. 새 키 쌍과 보관 위치는 별도 승인 뒤 만든다.
5. 필요한 보존 기간 동안 기존 백업과 구 키를 격리한다.
6. 새 키로 새 운영 백업과 테스트 복원 리허설을 완료한 뒤 교체 완료로 판정한다.

## 6. 운영 복원 필요 판단

현재 V1 절차에는 운영 D1 덮어쓰기 복원이 없다.

운영 복원이 필요해 보여도 다음 순서를 건너뛰지 않는다.

1. 읽기 전용 원인 조사
2. 최신 암호화 백업의 테스트 D1 복원
3. 데이터 차이 보고서
4. 운영 중단·쓰기 차단 방법 결정
5. 별도 운영 복구 계획 작성
6. 사용자 승인

이 runbook만으로 운영 DB import를 실행하지 않는다.

## 7. 날씨 migration·Worker 롤백

`0023_weather_snapshots.sql`은 새 날씨 테이블과 인덱스만 추가한다. 날씨 배포에 문제가 생기면 사용자·관리자 Worker를 동일한 이전 안정 SHA로 되돌리고 새 테이블은 삭제하지 않은 채 미사용 상태로 둔다. 운영 중 `DROP TABLE`이나 migration 되돌리기는 이 runbook으로 실행하지 않는다. 원인과 영향 범위를 확인한 뒤 별도 데이터 변경 계획과 사용자 승인을 받는다.
